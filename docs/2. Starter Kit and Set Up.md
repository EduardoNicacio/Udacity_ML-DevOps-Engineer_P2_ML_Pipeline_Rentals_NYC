## Choose a Repository Platform

Complete this project using either **GitHub** or **Azure DevOps (Azure Repos)**. Choose one platform and follow the corresponding setup instructions below. The project files, implementation requirements, and evaluation criteria are the same for both platforms.

### Option A: GitHub

1. Open the [Project Repository](https://github.com/udacity/build-ml-pipeline-for-short-term-rental-prices).

2. Select Fork to create a copy in your GitHub account.

3. Clone your fork, replacing `<your-github-username>` with your GitHub username:

    ```bash
    git clone https://github.com/<your-github-username>/build-ml-pipeline-for-short-term-rental-prices.git
    ```

### Option B: Azure DevOps

1. In Azure DevOps, create or open the project where you will store your work.

2. Import the public starter repository into Azure Repos:

    ```txt
    https://github.com/udacity/build-ml-pipeline-for-short-term-rental-prices.git
    ```

3. Copy the clone URL shown by Azure Repos and clone the imported repository:

    ```bash
    git clone https://dev.azure.com/<organization>/<project>/_git/build-ml-pipeline-for-short-term-rental-prices
    ```

For detailed import and authentication instructions, refer to the **GitHub to Azure DevOps Translation Guide** earlier in this course. Udacity does not provide an Azure DevOps organization. Follow your organization’s repository, security, and data-handling policies.

## Workspace and Component Environments

The Workspace notebook kernel and the environments used by MLflow steps are separate.

- `environment.yml` defines the development environment for local setup.
- The root `MLproject` references the root `conda.yml` for the main pipeline.
- Each component’s `MLproject` references its own environment file.
- `src/eda/MLproject` and `src/eda/conda.yml` provide a separate JupyterLab launch option for local EDA, as described in the repository README. In the Workspace, use the `ml` notebook kernel.

When a pipeline component uses a package, include it in that component’s `conda.yml`, even if the package is already installed in the Workspace notebook kernel.

## The Configuration

Pipeline parameters are in `config.yaml` (root of project).

The file is managed with **Hydra**.

- Example: `config["main"]["project_name"]` accesses the project name.
- **Do not hardcode values**; always read from `config.yaml`.

## Running the Pipeline

The commands below show how to select pipeline steps. The starter implements the download step; you will implement the remaining steps in the following pages. A successful command exit does not mean that unfinished steps have been implemented.

### Run Entire Pipeline

```bash
> mlflow run .
```

### Run a Specific Step

Example: only download:

```bash
> mlflow run . -P steps=download
```

### Multiple steps

```bash
> mlflow run . -P steps=download,basic_cleaning
```

### Override Config Parameters

Use Hydra syntax:

```bash
> mlflow run . \
  -P steps=download,basic_cleaning \
  -P hydra_options="modeling.random_forest.n_estimators=10 etl.min_price=50"
```

### Pre-Existing Components

Some components are already implemented in the repository’s `components/` directory. The default `main.components_repository` value in `config.yaml` is `components`, so the pipeline runs these local files from your clone. For example, the supplied download step calls `components/get_data`:

```yaml
_ = mlflow.run(
  f"{config['main']['components_repository']}/get_data",
  "main",
  env_manager="conda",
  parameters={
    "sample": config["etl"]["sample"],
    "artifact_name": "sample.csv",
    "artifact_type": "raw_data",
    "artifact_description": "Raw file as downloaded"
  },
)
```

## In Case of Errors

When an environment fails, identify the failing component and read the first dependency error in its logs. Check that component’s `conda.yml`, including its pip dependencies, and correct the specific dependency problem before rerunning the component.

The Workspace notebook kernel, local development environment, and MLflow component environments have different roles. They do not need identical Python or package versions. Follow the repository README for local troubleshooting.

If a failed environment must be recreated, identify its exact name or path from the MLflow logs and `conda info --envs`, then remove only that confirmed failed environment before retrying. Do not remove every environment whose name starts with `mlflow`; other projects may use them.
