# Submission Notes

Before submitting your project, complete the following steps:

1. Review the project rubric and confirm that you have completed all required steps.
2. Make your Weights & Biases (W&B) project public.
3. Add the URL of your public W&B project to both:
   - the project’s `README.md`; and
   - the **Submission Details (optional)** field.
4. Add the URL of the GitHub or Azure Repos repository that contains your work to both:
   - the project’s `README.md`; and
   - the **Submission Details (optional)** field.
5. In **Submission Details (optional)**, include:
   - **Repository platform**: GitHub or Azure DevOps; and
   - **Repository URL**: your GitHub or Azure Repos repository URL.
6. If you worked in the Workspace, commit and push your completed project to your own repository. Follow the submission instructions for your repository platform below.

Your submission must allow the reviewer to inspect your project files, commit history, and the `1.0.0` and `1.0.1` version markers.

## GitHub submissions

Make sure the reviewer can open your GitHub repository and its **Releases** page. Submit the repository through the normal project-submission workflow.

Before submitting, confirm that:

- the repository contains your final project files and commit history;
- the `1.0.0` release and corresponding Git tag point to the first released version of the pipeline; and
- the `1.0.1` release and corresponding Git tag point to the version containing the geographical-boundary fix.

## Azure DevOps submissions

New Azure DevOps public projects can no longer be created, so your Azure Repos URL might not be accessible to the reviewer. The URL identifies your source repository, but it does not provide the evidence needed to review a private repository.

Do not invite an unknown reviewer to your Azure DevOps organization, make confidential material public, or weaken your organization’s security controls. Instead, submit a complete-repository ZIP that preserves the Git history and annotated tags.

### 1. Create a fresh clone

After pushing your final code and tags to Azure Repos, clone the repository into a new directory on your local computer:

```bash
cd <parent-directory-for-your-submission>
git clone <your-azure-repos-clone-url> nyc-airbnb-submission
cd nyc-airbnb-submission
git fetch --all --tags
```

Use a fresh clone rather than your existing working directory. This helps ensure that the archive contains only files and Git history that were pushed to the submitted Azure Repos repository.

### 2. Verify the repository

Run the following commands from the fresh clone:

```bash
git status
git fsck --full
git tag -n
git cat-file -t 1.0.0
git cat-file -t 1.0.1
```

Confirm that:

- `git status` reports a clean working tree;
- `git fsck --full` reports no repository-integrity errors;
- `git tag -n` lists `1.0.0` and `1.0.1`; and
- each `git cat-file` command returns `tag`, confirming that the version marker is an annotated Git tag.

Also inspect `.git/config` and confirm that the stored remote URL does not contain a personal access token, password, or other credential. Do not include secrets, API keys, virtual environments, cached data, or confidential or proprietary files in your submission.

### 3. Create and verify the ZIP

Return to the parent directory and compress the entire fresh-clone directory, including its hidden .git directory:

```bash
cd ..
zip -r nyc-airbnb-submission.zip nyc-airbnb-submission \
  -x "*/.venv/*" "*/__pycache__/*" "*/.DS_Store"

unzip -t nyc-airbnb-submission.zip
unzip -l nyc-airbnb-submission.zip | grep "/.git/HEAD"
```

The final command must display an entry ending in `/.git/HEAD`. If it displays nothing, the ZIP does not contain the repository history and is not ready to submit. A source-only ZIP is not sufficient because it does not preserve the commits or annotated tag objects required for review.

### 4. Submit the project

Upload `nyc-airbnb-submission.zip` as your project submission. Include both of the following URLs in the project’s `README.md` and the **Submission Details (optional)** field:

- your public W&B project URL; and
- your Azure Repos repository URL.

In **Submission Details (optional)**, identify Azure DevOps as your repository platform, provide the Azure Repos URL, and state that the private repository is supplied as a complete-repository ZIP for offline review. Although the field is labeled optional, this information is required for an Azure DevOps submission.

For example:

```md
Repository platform: Azure DevOps
Repository URL: https://dev.azure.com/<organization>/<project>/_git/<repository>

This repository is private. I uploaded a complete-repository ZIP containing the .git directory for offline review.
```

The Azure Repos URL does not need to be accessible to the reviewer. The complete-repository ZIP supplies the project files, repository history, and version-tag evidence needed for offline review.

Once you have completed the instructions for your selected platform, you are ready to submit your project.
