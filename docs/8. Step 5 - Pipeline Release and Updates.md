# Step 5: Pipeline Release and Updates

## Step 1: Visualize the Pipeline

After running the pipeline, you can use W&B to understand how data flows through each step and how the final model is produced. To do this, navigate to your W&B project page, open the Artifacts section, and select the random_forest_export artifact. Then click on the Lineage tab.

Pipeline diagram showing sequential steps: downloading raw data, cleaning data, splitting into train/validation sets, training a random forest model, exporting the model artifact, and finally testing the model, with corresponding artifacts produced between steps.
![Visualization of the pipeline](https://video.udacity-data.com/topher/2023/December/656d2d46_screenshot_5/screenshot_5.jpeg)
<center>Visualization of the pipeline</center>

In this view, W&B displays a graph that represents the entire pipeline. Each green node corresponds to a run (a processing step such as cleaning, splitting, or training), while each blue node represents an artifact (such as datasets or models) created and passed between steps. By following the connections from left to right, you can trace how the raw data is transformed step by step into the final trained model.

As you examine the graph, make sure that the pipeline is connected as expected. The model artifact should be produced by the `train_random_forest` step, which in turn should consume the training data generated by the `train_val_test_split` step. That training data should originate from the cleaned dataset produced by the `basic_cleaning` step, which ultimately depends on the original raw dataset. If any connection is missing or incorrect, it may indicate an issue in how the pipeline is configured.

This lineage view is important because it guarantees that your pipeline is reproducible and traceable. It allows you to verify that the model was trained on the correct data and helps you quickly identify where problems occur if results are unexpected.

## Step 2: Release the Pipeline

Select the best hyperparameters using validation MAE and save them as the default values in `config.yaml`. Commit and push that configuration with your pipeline code before creating version `1.0.0`; the release tag must point to that commit. Follow the instructions for your repository platform.

### GitHub

In your GitHub repository, open **Releases** and create a release named `1.0.0`. Ensure that the release creates a Git tag named `1.0.0`. If needed, follow the [GitHub release instructions](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository#creating-a-release).

![GitHub release form highlighting the version tag, release title, and description](https://video.udacity-data.com/topher/2026/August/6a719f5c_github-release-highlighted/github-release-highlighted.jpg)
<center>Enter the `1.0.0` tag and confirm the target branch (1), provide a release title (2), and describe the released pipeline (3).</center>

### Azure DevOps

Azure Repos uses Git tags as version markers instead of the GitHub Releases interface. Create an annotated tag named 1.0.0 for the release commit and push it to Azure Repos:

```bash
git tag -a 1.0.0 -m "Pipeline release 1.0.0"
git push origin 1.0.0
```

In Azure DevOps, open your repository and select **Repos > Tags**. Confirm that `1.0.0` appears in the tag list and points to the intended release commit.

![Azure Repos Tags page showing the annotated pipeline version 1.0.0](https://video.udacity-data.com/topher/2026/August/6a719eb5_07-pipeline-release-tag-highlighted/07-pipeline-release-tag-highlighted.jpg)
<center>Open **Repos > Tags** (1), then confirm that the `1.0.0` tag (2) points to the commit containing the released pipeline configuration.</center>

If you later discover issues or make improvements, update the code and create a new release with an incremented version number such as `1.0.1`, `1.0.2`, and so on. This versioning approach allows you to track changes over time while preserving the ability to reproduce previous results.

## Step 3: Train the Model on a New Data Sample

Now that you have created version `1.0.0` of your pipeline, verify that it can be executed independently using MLflow. This simulates how the pipeline would be used in a production setting, where only a released version is available.

Run the pipeline from your remote repository at version `1.0.0`. In this step, you will intentionally use a different dataset, `sample2.csv`, to validate that the pipeline behaves correctly when it receives new data. Use the command for your repository platform.

### GitHub

```bash
mlflow run https://github.com/<your-github-username>/build-ml-pipeline-for-short-term-rental-prices.git \
  -v 1.0.0 \
  -P hydra_options="etl.sample='sample2.csv'"
```

### Azure DevOps

```bash
mlflow run https://dev.azure.com/<organization>/<project>/_git/build-ml-pipeline-for-short-term-rental-prices \
  -v 1.0.0 \
  -P hydra_options="etl.sample='sample2.csv'"
```

The Azure Repos command requires your Git client to be authenticated to the repository. Follow the authentication guidance in the **GitHub to Azure DevOps Translation Guide** and your organization’s security policies.

The pipeline will fail when you run version `1.0.0`. This is expected.

The failure occurs because the `test_proper_boundaries` validation test detects data points outside the allowed geographical boundaries. In other words, the pipeline is correctly identifying that the new dataset contains invalid data.

This is an example of a **successful failure**: the pipeline is doing its job by catching bad input data before it propagates to later steps.

#### Fix the Geographical Boundary Issue

Update `src/basic_cleaning/run.py` by extending the cleaning logic you implemented in Step 2. Keep the existing price filtering and `last_review` datetime conversion from your EDA.

After the existing cleaning operations and before saving `clean_sample.csv`, add this geographical boundary filter:

```python
idx = df["longitude"].between(-74.25, -73.50) & df["latitude"].between(40.5, 41.2)
df = df[idx].copy()
```

Retain the rest of your existing cleaning, CSV-save, and W&B artifact-upload logic.

#### Create Version 1.0.1

Commit and push the boundary-filter change to your remote repository. Then create version `1.0.1` using the instructions for your repository platform.

**GitHub**
In your GitHub repository, create a new release named `1.0.1` with a corresponding Git tag named `1.0.1`.

**Azure DevOps**
Create and push another annotated Git tag:

```bash
git tag -a 1.0.1 -m "Pipeline release 1.0.1"
git push origin 1.0.1
```

Confirm that `1.0.1` appears under **Repos > Tags** and points to the commit containing the boundary-filter change.

#### Run the Updated Version

Run the pipeline again using version 1.0.1.

**GitHub**

```bash
mlflow run https://github.com/<your-github-username>/build-ml-pipeline-for-short-term-rental-prices.git \
  -v 1.0.1 \
  -P hydra_options="etl.sample='sample2.csv'"
```

**Azure DevOps**

```bash
mlflow run https://dev.azure.com/<organization>/<project>/_git/build-ml-pipeline-for-short-term-rental-prices \
  -v 1.0.1 \
  -P hydra_options="etl.sample='sample2.csv'"
```

This time, the pipeline should run successfully. The successful run confirms that the pipeline can process the new data safely and that its validation and cleaning logic work as intended.
